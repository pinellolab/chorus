it holds the earlier PR's content *plus* its own.

## Findings

### F1 — `device='cuda:N'` overrides an outer `CUDA_VISIBLE_DEVICES` mask (P1, pre-existing)

Four templates do `os.environ['CUDA_VISIBLE_DEVICES'] = device.split(':')[1]`:
`chrombpnet_source/templates/{load,predict}_template.py` and
`cherimoya_source/templates/{load,predict}_template.py`.

If a scheduler grants `CUDA_VISIBLE_DEVICES=4,5` and the caller asks for `device='cuda:1'`
meaning "the second GPU I was given" (physical 5), the template sets the mask to `1` absolutely
and the process lands on **physical GPU 1 — a device it was not granted.** Not hypothetical on
this host: GPU 4 was another tenant's for the whole audit.

The checklist has carried this as a P1 for several audits and it is still open. Fix: do not
touch the variable. Torch already interprets `cuda:N` within the visible set, so passing the
string through is correct; for the TF path, remap `N` through the existing mask
(`os.environ['CUDA_VISIBLE_DEVICES'].split(',')[N]`) instead of replacing it.

### F2 — `extract_sequence_with_padding` silently returns a SHORT sequence near a chromosome end (P1, new)

The function has two branches and only one of them handles the chromosome boundary.

When `region_length >= total_length` it "trims from centre" and calls
`fasta.fetch(chrom, start+trim, start+trim+total_length)` with **no bounds check**. pysam
silently clamps to the chromosome, so the caller gets fewer bases than it asked for — and the
metadata it returns hardcodes `{'leftN': 0, 'rightN': 0}`, reporting that no padding was
needed. Measured on chr1 (length 248,956,422), asking for 2,114 bp:

| interval start | returned | asked |
|---|---|---|
| `L − 2114` | 2,114 bp | 2,114 |
| `L − 1000` | **1,000 bp** | 2,114 |
| `L − 40` | **40 bp** | 2,114 |

The other branch (`region_length < total_length`) pads with N correctly and returns 2,114 in
all three cases, so the fix is to apply the same bounds handling in the first.

Callers: `chorus/utils/sequence.py:500` (the variant-window builder) and
`chorus/oracles/sei.py`, which passes `total_length=SEI_WINDOW` — so a Sei prediction at a
telomere can reach the model with a short one-hot. Silently returning the wrong length is worse
than raising, which is what the raw `extract_sequence` does.

### F8 — The Enformer example is not reproducible, but Enformer's forward pass is (P1, new)

**The first half of this finding is what I originally wrote down, and it was too broad.** Both
halves are stated because the narrowing is the useful part.

**What is not reproducible.** Two runs of `scripts/regenerate_examples.py --oracle enformer` —
identical code, separate processes, same host — produce different committed output:

```
596 numeric differences in example_output.json,  median 0.0159%
ref_value       max 0.067%
raw_score       max 4.29%      (log2FC amplifies a near-zero denominator)
quantile_score  max 0.69%
```

**What *is* reproducible.** A single-region, single-track Enformer prediction is bitwise
identical, and not only back-to-back — across separate processes too, compared on the raw
float32 bit patterns:

| check | result |
|---|---|
| `predict()` twice in one process (896 values) | **bitwise identical** |
| `predict()` in two separate processes (first 64 bins, as uint32) | **bitwise identical** |
| cherimoya `predict()` twice, 2,114 values | **bitwise identical** |
| chrombpnet `predict()` twice, 2,114 values | **bitwise identical** |

So this is not the AlphaGenome/XLA cross-process story that §13 documents, and it is not the
forward pass. **The mechanism is not localised.** The remaining candidates, in the order I
would check them, are the multi-track batched path (the example scores many tracks at once,
where batch composition can change reduction order), the window handling inside
`predict_variant_effect`, and TensorFlow retracing — a retrace warning does appear in that path.

Two things follow regardless of the cause. `examples/walkthroughs/variant_analysis/SORT1_enformer/`
cannot be regenerated reproducibly, so a diff on it after an unrelated change shows ~400 moved
values that are not attributable to that change — which is exactly what happened during #180's
regeneration, and why that PR's "no number moved" claim had to be established a different way.
And `scripts/gate_end_to_end_determinism.py` does not catch it, because an in-process check
cannot: the forward pass it would compare is deterministic.

Not filed as an issue, by the maintainer's decision; recorded here instead.

## Corrections to the checklist itself

Six items are stale enough to produce false findings. Left as-is here and listed for a separate
edit, since changing the checklist mid-audit would make this run unrepeatable.

1. **§7 `<details>`** — "grep -c '<details' returns 0 in every shipped report" is no longer
   true: the multi-oracle report has four legitimate `<details class='oracle-block'>` wrappers,
   one per oracle. The P2 about the "How to read" collapsible should be scoped to that block.
2. **§15 CDN grep** — `grep -rn 'cdn\|googleapis\|...'` matches `storage.googleapis.com`
   **inside the inlined igv.min.js** (its Google Cloud Storage support code) and so fires on
   all 19 IGV reports. Same false-positive class as the `igv.org` string. The reliable check
   now exists: the measured request inventory in
   `tests/test_reports_bundle_their_genome.py`.
3. **§10 `examples/applications/` (P0)** — three live hits, all explanatory: two in
   `tests/test_rerender_refuses_to_degrade.py` (the test that exists *because* the path was
   removed) and one comment in `scripts/rerender_examples.py`. The rule should read "must not
   appear as a path users are pointed at".
4. **§2 `list_tracks`** — it is an **MCP tool**, not `chorus.list_tracks`; the Python API has
   no such symbol. Verified working with no token, but the item should say where it lives.
5. **§17 "pins every dep"** — a naive check reports two unpinned entries: the literal `pip`
   (not a dependency) and `coolbox @ git+…@651b930` (pinned to a commit, which is a stronger
   pin than a version range). Both are fine; the item needs the exception noted.
6. **§14 "should pad / clamp gracefully"** — the raw `extract_sequence` *raises* at a boundary
   and that is correct; padding is `extract_sequence_with_padding`'s job. The item should name
   which function it means, and note F2.
