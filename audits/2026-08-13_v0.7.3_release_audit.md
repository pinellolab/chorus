## The finding

### G1 — F1 was fixed in the templates only; the **direct** load path still overwrote the mask

`ChromBPNetOracle._load_direct` and Enformer's in-process load still did the exact thing the
previous audit's F1 was about:

```python
gpu_id = self.device.split(':')[1]
os.environ['CUDA_VISIBLE_DEVICES'] = gpu_id
```

`use_environment=False` is the **`create_oracle` default**, so if anything this is the more
important half of the two.

**Why it survived a fix and a guard.** The guard I wrote for F1 enumerated
`chorus/oracles/*_source/templates/*template.py`. The checklist item that prompted F1 said
"the TF and Cherimoya **templates** assign…", and I scoped the search to what it named instead
of to the property it was about. The enumeration was over the wrong set — which is the same
mistake in miniature that F1 and #125 both exist to prevent.

**Fixed and shipped in v0.7.3** (PR #185): one shared
`chorus.core.platform.resolve_visible_ordinal`, which remaps `N` through whatever mask is set,
passes it through when there is none, and raises naming what `N` indexes when out of range.
Verified under `CUDA_VISIBLE_DEVICES=2,3`: `cuda:0` → physical 2, `cuda:1` → physical 3. The
guard now enumerates `chorus/oracles/*.py` as well, and is mutation-tested against
reintroducing the defect.

**Not a regression and not a v0.7.3 defect**: it predates every release and only fires when a
caller passes `device='cuda:N'` explicitly. Default usage never reached it.

The eight builders under `scripts/` were checked in the same sweep and are **already correct** —
they guard on `if os.environ.get("CUDA_VISIBLE_DEVICES") in (None, "")`, so an explicit mask
wins, exactly as `CLAUDE.md` records.

## One transient failure, and why it was not real

The first integration run reported **144 passed, 1 failed**:
`test_a_report_is_bit_exact_across_two_processes`, with
`CUDA_ERROR_OUT_OF_MEMORY` from AlphaGenome.

It was contention I caused: the notebook re-execution (§6) was running concurrently, and
`scripts/gate_end_to_end_determinism.py` spawns two AlphaGenome processes of its own with JAX
preallocating. Re-run in isolation it passed in 3 m 38 s, and a clean serial run of the whole
integration suite gave **145 passed, 0 failed**. Both results are recorded rather than only the
good one.

Worth knowing for the next audit: **do not run the notebooks and the integration suite at the
same time**, even on different `CUDA_VISIBLE_DEVICES` — that gate script sets its own mask
(`--gpu`, default `1`) and will not stay where you put it.

## Found by an adversarial verification pass, after the tag had moved

Six release claims were re-verified by independent read-only agents, each then challenged by a
second agent told to refute it. Four claims held; the challenges found five real problems the
first pass had certified as fine, which is the argument for running the second pass at all.

**R1 — the Release was published against a commit the notes do not describe (P1, process).**
`v0.7.3` was published 13 s after commit `58ff961`, and the tag was later force-moved two
commits on to `a79feb0`. For the ~8.5 h in between, `git fetch --tags` or the release tarball
gave a tree with **neither** the F1 direct-path fix **nor** G1 — the two things the notes lead
with. Proof: `git show 58ff961:chorus/core/platform.py | grep -c resolve_visible_ordinal` = 0.
The same pattern holds for **v0.7.2** (published 01:48:43Z, tag object dated 13:44:25Z), so it
is a recurring release-process defect rather than a one-off. The tell is only visible in the
API: `createdAt` is tag-derived, so `createdAt` later than `publishedAt` means the tag moved
after publication. Added to the checklist as a §19 item.

**R2 — 575 characters of superseded prose shipped in the published notes.** The `cuda:N` entry
kept a verbatim tail of its own pre-rewrite version, duplicating five phrases and contradicting
the corrected opening by blaming "six oracle templates" alone. Proved residue rather than
intent: the tail is a substring of `git show 3132556:CHANGELOG.md`. Removed, notes regenerated.

**R3 — the `[Unreleased]` compare link still pointed at `v0.7.1`**, having skipped two releases.

**R4 — `normalization.py`'s "Release ↔ revision" table stopped at 0.7.2**, so the code's own
record of which artefact revision each release pairs with omitted this one. Row added.

**R5 — three modules still claimed a report needs no network**, after #139 was supposed to have
retired that claim: `_igv_report`'s module docstring ("self-contained HTML page", and gene
annotations coming "from hg38 automatically via IGV's built-in genome" — both false since the
gene track became inline GENCODE), and a comment in `causal.py`. Corrected, and
`tests/test_docs_do_not_reclaim_offline.py` now makes the claim load-bearing.

That guard is worth a note of its own, because the first version of it **failed twice**: it
flagged three correct lines (base64 PNGs are genuinely self-contained; "listing tracks works
offline" is true of vendored metadata; the `CHORUS_IGV_SEQUENCE_URL` docstring describes how to
*make* a site offline-capable), and once its allowlist was wide enough to let those through, a
reintroduced false claim slipped past because a nearby line happened to contain the word
"sequence". It is now a blocklist of the exact wordings that shipped, with named exemptions, and
it is mutation-tested in both directions — it must catch each historical wording and must leave
each true statement alone.

**Also fixed:** three committed notebook outputs still printed `Chorus version: 0.7.2`. Replaced
with the 0.7.3 executions from this audit's own §6 run, so no GPU time was spent twice.

**Two edge cases in the new resolver**, both found by the refuters: `resolve_visible_ordinal`
used raw list indexing, so `cuda:-1` resolved silently to the last visible device; and after a
`device='cpu'` load had set the mask to `-1`, a later `cuda:0` returned `-1` and would have run
on the CPU while reporting success. Both now raise.
